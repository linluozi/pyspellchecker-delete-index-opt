1The defect

pyspellchecker is a pure-Python spell checker based on Peter Norvig's essay. SpellChecker.candidates(word) returns the dictionary words within two edits: first it tries the word itself, then its edit-distance-one neighbourhood, and only if that is empty does it fall back to distance two.

That fallback is implemented as a second, full expansion of the same neighbourhood:

def __edit_distance_alt(self, words):
    tmp = [w if self._case_sensitive else w.lower() for w in words if self._check_if_should_check(w)]
    return [e2 for e1 in tmp for e2 in self.known(self.edit_distance_1(e1))]

For the bundled English dictionary the edit-distance-one neighbourhood is 675 strings for a 7-letter word and 1,125 for a 12-letter word. Growing each of those a second time means building and dictionary-testing on the order of |E1|² — around 600,000 strings for a single input word.

2Which distance is it, really?

Before replacing anything, the exact semantics have to be pinned down. The candidate set is not Levenshtein, and it is not OSA (optimal string alignment) either. Because the two edits are generated layer by layer, a deletion may be followed by a transposition of two characters that were not adjacent in the original word — exactly the case OSA forbids. 

alot  →  aot   (delete 'l')
      →  oat   (transpose 'a','o')     2 edits · OSA would say 3

Verified against the untouched code: "oat" is returned for "alot". So the real distance is unrestricted Damerau-Levenshtein. A replacement that verifies with an OSA DP silently loses candidates — the first prototype of this patch did exactly that and disagreed with upstream on alot, thier and libary.

3The fix

A delete-variant reverse index. Every dictionary word is indexed under itself and under each string obtained by deleting one of its characters; reading index[t] then answers "which dictionary words are one insertion away from t?" in O(1).

Why this is exact. If two strings are at Damerau-Levenshtein distance ≤ 1, their sets of "at most one deletion" variants intersect. So for every one-edit variant e1, the words within one edit of e1 are precisely the union of index[t] over t in the one-deletions of e1.

for e1 in edit_distance_1(word):
    hits |= index[e1]                                  # every entry is ≤ 1 insertion away
    for t in deletes_of(e1):
        hits |= {w for w in index[t] if within_one_edit(e1, w)}   # linear check, not a DP

within_one_edit is an O(n) predicate — a single substitution, a swap of two neighbouring characters, or a single insertion/deletion — and it only runs on the handful of entries the index actually returns.

Two design choices worth naming

  • One deletion, not two. A two-delete index would cut the query side from ~8,000 lookups to a few dozen, but it needs 7,678,646 entries — 4.9× the 1-delete index, on the order of half a gigabyte at the density measured below. Hopping through edit_distance_1 first buys the same completeness for 1,369,364 entries.
  • A bucket is a bare string until a second word maps to it, then becomes a list. That halves the index: +102.6 MB instead of +201.6 MB, and builds in 0.79 s instead of 1.20 s.
  • The index is built lazily on the first distance-2 query and dropped whenever the dictionary changes, so a dictionary that is only ever queried for correct or one-edit words never pays for it.

The whole change is one file — spellchecker/spellchecker.py, about 120 added lines. Nothing else in the package was touched; LICENSE is byte-identical to upstream (sha1 39f9d947…), and the modifications are listed in NOTICE.md.

Cold start, measured end to end on three long typos: 827.8 ms for the first pass (of which ~790 ms is the build), then 3.1 ms per word afterwards. Upstream spends ~350 ms on the first word and ~347 ms on every word after it.

The trade is deliberate and stated plainly: ~103 MB of memory and one 0.8 s build buy a hundredfold cut on the path that used to cost half a second per word.

The harness was poison-tested

An equivalence harness that always passes proves nothing. Disabling the within_one_edit verification in the patched build — so every index hit is accepted — makes this same harness report hundreds of mismatches, for example bda → ['abab', 'abc', 'abcd', 'dabc'], which upstream never returns. The zero-difference results above are therefore meaningful.

Reproduce the poison run with python bench/exhaustive.py --alpha abcd --maxlen 7 --poison.
